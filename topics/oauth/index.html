OAuth 2.0

How third-party apps get permission to act on your behalf — without ever seeing your password. A protocol about delegated authorization, not authentication.

01The problem

You want a calendar app to read events from your Google account. The naive solution is to hand it your Google password. That's a disaster: the app can do anything as you, forever, and rotating your password means re-entering it in every connected app.

OAuth 2.0 splits this into two things: authentication (proving who you are to Google — Google's problem) and delegation (Google telling the calendar app "this user said you can read their events"). The calendar app gets a token, not a password. The token is scoped, expirable, and revocable.

02The four roles

Every OAuth flow has the same cast:

Resource owner
You. The human who owns the data.
Client
The app that wants access — the calendar app in the example.
Authorization server
Issues tokens. Google's accounts service. Asks you to consent.
Resource server
Holds the data. The Google Calendar API. Verifies tokens.

The authorization server and resource server often live at the same company but are conceptually distinct — one mints tokens, the other accepts them.

03The flow that matters

OAuth 2.0 originally specified four flows. Today, you should use exactly one: the Authorization Code Flow with PKCE. Implicit flow is dead. Password grant is dead. Client credentials is for machine-to-machine, not user delegation. OAuth 2.1 codifies this.

1
CLIENT → BROWSER App generates a random code_verifier, derives code_challenge = SHA256(verifier), and redirects you to the authorization server with the challenge attached.
2
BROWSER → AUTH SERVER You log in (if not already) and see a consent screen: "Calendar App wants to read your events." You approve.
3
AUTH SERVER → BROWSER → CLIENT The auth server redirects back to the app's redirect_uri with a short-lived authorization_code in the URL.
4
CLIENT → AUTH SERVER (back channel) App POSTs the code and the original code_verifier to the token endpoint. Server checks SHA256(verifier) matches the challenge from step 1.
5
AUTH SERVER → CLIENT Server returns an access_token (and usually a refresh_token). The auth code is now burned.
6
CLIENT → RESOURCE SERVER App calls the API: Authorization: Bearer <access_token>.

Why PKCE?

Step 3 puts the auth code in a URL, which means it can leak — browser history, server logs, a malicious app intercepting the redirect on a mobile OS. PKCE makes the leak useless: an attacker who steals the code can't redeem it without the original verifier, which never left the client.

Originally PKCE was a public-client patch (mobile, SPAs). Now it's recommended for all clients, including ones with a secret.

04The tokens

access_token
Short-lived (minutes to an hour). Sent on every API call. Treat like a password: never log it, never expose to JS you don't trust. Often a JWT, but the spec doesn't require any format — to the client, it's an opaque string.
refresh_token
Long-lived (days to forever). Used only at the token endpoint to get a new access token. Should be more protected than access tokens — leaking one means persistent access. Rotate on every use if you can.
id_token
Not OAuth — OpenID Connect. A signed JWT describing who logged in (subject, email, etc). For the client to know who the user is, not for talking to APIs. If you only need login, you want OIDC, not raw OAuth.

05Mistakes everyone makes

  • Using OAuth for authentication. OAuth proves the user authorized an app — not that the user is present at the client right now. Use OpenID Connect for "log in with Google."
  • Storing tokens in localStorage in an SPA. Any XSS reads them. Prefer a backend-for-frontend pattern: cookies with HttpOnly; Secure; SameSite, server proxies the API.
  • Skipping the state parameter. Without it, the redirect from the auth server is unauthenticated. Use state as a CSRF token tied to the user's session.
  • Wildcard redirect URIs. Every accepted redirect URI must be a registered, exact match. Open redirects in your app become token theft.
  • Never rotating refresh tokens. If a refresh token leaks and you don't rotate, the attacker has access forever. Rotate on every use and revoke the chain on detected reuse.
  • Confusing scopes with permissions. A scope is what the user consented to. Your resource server still has to enforce that this user can actually access this resource.

06Which flow, when

Web app with a backend
Authorization Code + PKCE. Tokens live server-side; browser only sees a session cookie.
SPA with no backend
Authorization Code + PKCE, but seriously consider giving it a backend. Bearer tokens in a browser are a recurring footgun.
Mobile / desktop app
Authorization Code + PKCE, via the system browser (not a webview). Use the platform's app-link mechanism for the redirect.
CLI tool
Authorization Code + PKCE with a loopback redirect (http://127.0.0.1:<random-port>), or device code flow if you can't open a browser.
Server-to-server, no user
Client Credentials. No human in the loop, no delegation — just an app proving who it is.
Just want "log in with Google"
OpenID Connect (which builds on Authorization Code + PKCE).

07The shortest mental model

Three sentences. OAuth gives a token to an app so it can act on your behalf, scoped to what you agreed to. The token is obtained through a redirect dance that keeps your password out of the app's hands and the token out of the URL bar. Everything else — PKCE, state, refresh rotation, BFF — is hardening that dance against a specific attack.
