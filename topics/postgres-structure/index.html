Deep dive

How Postgres Is Structured

Everyone says database, schema, and table loosely — and then gets surprised when a query can't see another database, or when everything lands in public and collides. Postgres has a precise nesting. Once you can name every layer, the surprises stop.

01The question this answers

Where does a row actually live? You connect to "a database," you create "a table," and somewhere on disk there are files. Between the connection string and the bytes there are four named containers, nested one inside the next, plus a second set of objects that sit outside that nesting and are shared by everything. Confusing the two is the root of most "wait, why can't I…" moments.

The whole structure is also self-describing: Postgres stores the definition of every database, schema, table, and column as rows in ordinary tables that you can query. Understanding the nesting and the catalog together is understanding the whole shape of the system.

02The nesting, named

Five containment levels. The outermost is a single running server; the innermost is a row. Each level lives strictly inside the one above it.

Cluster
one running PostgreSQL server — one data directory, one set of processes, one port
Confusingly, this is not a cluster of machines. It's a single instance. Created by initdb.
Database
myapp — an isolated namespace tree; ships with postgres, template0, template1
One connection attaches to exactly one database. You can't query across databases in plain SQL.
Schema
public — a namespace inside a database; holds tables, views, functions, types…
A database can have many schemas. search_path decides which one an unqualified name resolves to.
Relation
users — a table (also: view, index, sequence — all "relations")
Row (id=42, email='…') — a single tuple, the actual data
Cluster-global, beside the tree: roles/users, tablespaces, and the list of databases themselves. These are shared by every database — they are not inside any one of them.

Read it as nesting dolls: cluster → database → schema → relation → row. A fully-qualified name walks part of that path: schema.table (and, inside one database, that's as far as references go — there's no database.schema.table you can query from another database).

03The mistake MySQL trained into you

In MySQL, database and schema are the same thing — CREATE SCHEMA and CREATE DATABASE are synonyms. In Postgres they are different levels of the nesting, and this trips up nearly everyone arriving from MySQL.

A Postgres database is a hard boundary: separate catalog, separate connection, no cross-database joins in standard SQL. A Postgres schema is just a namespace inside a database — a folder for tables. You join across schemas freely; you cannot join across databases without an extension (postgres_fdw or dblink) that opens a second connection under the hood.

So a MySQL "database" maps to a Postgres schema, not a Postgres database. Internalize that one sentence and half the confusion evaporates.

04Schemas and the search_path

When you write SELECT * FROM users with no schema prefix, Postgres has to decide which schema's users you mean. It walks the search_path — an ordered list of schemas — and uses the first match. 

-- default search_path
SHOW search_path;        -- "$user", public

-- $user expands to a schema named after the connected role,
-- if one exists; otherwise it's skipped. Then public.

-- unqualified: resolved via search_path
SELECT * FROM users;

-- qualified: unambiguous, ignores search_path
SELECT * FROM analytics.users;

Schemas earn their keep when you want logical separation without the hard wall of separate databases: grouping a large app into modules (billing, auth, reporting), giving each tenant its own schema while still sharing one connection pool and joining across them, or isolating an extension's objects. The public schema is just the default one — not special, and on modern Postgres no longer writable by every role by default.

05What actually lives in a schema

"Schema holds tables" is the common shorthand, but a schema is a namespace for many object kinds, and they share that namespace — you can't have a table and a view with the same name in the same schema:

  • Tables and partitioned tables — the rows.
  • Views and materialized views — stored queries; the materialized kind caches results on disk.
  • Indexes — separate on-disk structures that point back at table rows.
  • Sequences — the counters behind serial / GENERATED … AS IDENTITY.
  • Functions, procedures, types, operators, domains — also namespaced by schema.

Tables, views, indexes, sequences, and materialized views are collectively called relations — and Postgres tracks every one of them in a single catalog table, which is the next piece.

06The catalog: Postgres describes itself

Here's the part that makes the whole structure click: the metadata about your databases, schemas, tables, and columns is itself stored in ordinary tables. They live in a schema called pg_catalog, which is implicitly always on the search_path.

pg_database — one row per database in the cluster.
pg_namespace — one row per schema.
pg_class — one row per relation (table, index, view, sequence…).
pg_attribute — one row per column.
pg_authid — one row per role.

Every object has an oid (object identifier) that ties these tables together. The nesting from section 02 is literally foreign-key-shaped relationships between these catalog tables. 

-- "list my tables" is just a query against the catalog
SELECT n.nspname AS schema, c.relname AS name
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r'          -- 'r' = ordinary table
  AND n.nspname NOT IN ('pg_catalog', 'information_schema');

There's also information_schema — a set of standardized, SQL-spec views over the same data, more portable but less detailed than the native pg_* catalogs. The psql shortcuts (\l databases, \dn schemas, \dt tables) are just pre-written catalog queries.

07Global vs. per-database

The single most useful distinction: some objects belong to the whole cluster and are visible from every database; others live inside one database and are invisible from the others.

ObjectScopeWhy it matters
Roles / userscluster-globalOne role logs into any database. You don't recreate users per database.
Tablespacescluster-globalStorage locations are shared; any database can place objects in one.
Databasescluster-globalThe list of databases is a cluster-level catalog (pg_database).
Schemasper-databaseA schema exists inside one database only.
Tables / views / indexesper-databaseCannot be seen or joined from another database in plain SQL.
Extensionsper-databaseInstalled into a specific schema of a specific database.

This is exactly why "create a user" works once for the whole server, but "create the orders table" has to happen inside the right database.

08How it lands on disk

The logical nesting maps onto a directory tree under the data directory (PGDATA): 

$PGDATA/
  base/<database-oid>/<relfilenode>   # one dir per database; files per relation
  global/                            # cluster-wide catalogs (roles, databases)
  pg_wal/                            # the write-ahead log
  pg_tblspc/                         # symlinks out to tablespaces

Each table or index is stored as one or more 1 GB segment files, carved into fixed 8 KB pages — the unit Postgres reads and writes. Values too large to fit in a page get pushed to a side table via TOAST (compression + out-of-line storage), transparently. A tablespace just lets a relation's files live on a different disk/path, represented as a symlink under pg_tblspc/.

oid vs relfilenode — the file-hunting gotcha

Every relation has a stable oid, but the file on disk is named by its relfilenode. They start equal, then diverge whenever a relation is rewritten (VACUUM FULL, TRUNCATE, CLUSTER). To find a table's actual files, ask the catalog with pg_relation_filepath('users') rather than assuming the filename matches the oid.

09One table that's secretly many

Declarative partitioning bends the "one table = one set of files" picture. A partitioned table is a logical parent with no storage of its own; rows physically live in child partition tables, routed by a key: 

-- parent: defines the shape and the partition key, stores nothing
CREATE TABLE events (id bigint, ts timestamptz, body text)
  PARTITION BY RANGE (ts);

-- children: each is a real table holding a slice of the rows
CREATE TABLE events_2026_q1 PARTITION OF events
  FOR VALUES FROM ('2026-01-01') TO ('2026-04-01');

Queries hit the parent; Postgres prunes to the relevant children. Each partition is still an ordinary relation in the catalog with its own files — the parent is the abstraction layered on top. (Older code may use table inheritance, the manual precursor; reach for declarative partitioning today.)

10Mistakes everyone makes

  • Treating database and schema as interchangeable. Especially coming from MySQL. A new database is a hard wall; a new schema is a folder. Pick on purpose.
  • Expecting cross-database queries. SELECT … FROM otherdb.public.t doesn't work. If you need to query across them, you wanted schemas in one database — or you'll be wiring up postgres_fdw.
  • Dumping everything into public. It works until names collide, permissions get muddy, and an extension drops its objects in beside yours. Group related objects into named schemas early.
  • Trusting search_path for correctness or security. A mutable search path means an unqualified name can resolve somewhere unexpected. In SECURITY DEFINER functions, set an explicit search_path or schema-qualify everything.
  • Hunting for a table's file by its oid. The on-disk name is the relfilenode, which drifts from the oid after rewrites. Use pg_relation_filepath().
  • Assuming a schema is a security boundary. It's a namespace. Access is controlled by GRANT/REVOKE on the schema and its objects, not by the nesting alone.

11New database, new schema, or neither?

Separate database
Hard isolation. Truly unrelated apps, separate backup/restore lifecycles, no need to ever join the data together. Cost: no cross-querying without an FDW, and per-database setup of extensions and grants.
Separate schema (same database)
Logical grouping with shared reach. Modules of one app, or per-tenant separation where you still want one connection pool and the ability to query across tenants. The default answer for "I want to organize my tables."
Neither — just one schema
Small or single-purpose. A modest app rarely needs more than public plus maybe one or two named schemas. Don't manufacture structure you won't use.
Partition an existing table
One huge table by a natural key. Time-series, or data you routinely query and age out by range/list. Structure for performance and retention, not for organization.

12The shortest mental model

A Postgres server is one cluster; a cluster holds databases; a database holds schemas; a schema holds tables and other relations; a relation holds rows — and your connection lives inside exactly one database, so it can cross schemas but never databases. Roles and tablespaces sit outside that tree, shared by the whole cluster. And the entire map is kept as rows in the pg_catalog tables, which means Postgres can answer every question about its own structure with a query.
